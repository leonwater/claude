# 파일 기반 AI 퀴즈 학습 앱 — 개발 파이프라인 설계

> 목표: 파일을 올리면 AI가 내용을 그대로 숙지하고 객관식 문제를 내주는 모바일 앱.
> 출퇴근·짧은 이동 시간에 한 손으로, 신호가 약한 곳에서도 풀 수 있어야 한다.

---

## 0. 한눈에 보기

```
[앱] 파일 선택(여러 개)
   │  업로드 (presigned URL, 이어올리기)
   ▼
[서버] ① 수집·파싱 ──► ② 원문 청크 저장 ──► ③ 문제은행 생성(LLM) ──► ④ 검증
                                                                      │
   ┌──────────────────────────────────────────────────────────────────┘
   ▼
[앱] 문제은행 다운로드(오프라인 저장) ──► ⑤ 퀴즈 세트 구성(10/20/30/40)
                                         │
                                         ▼
                                   ⑥ 채점 ──► ⑦ 오답노트(정답률 추적, 70% 초과 시 졸업)
```

핵심 설계 원칙 세 가지:

1. **원문은 절대 가공하지 않는다.** 요약·재작성 없이 추출한 텍스트를 그대로 저장하고, 모든 문제는 원문 문장을 근거로 인용해야 통과한다.
2. **문제는 미리 만들어 둔다.** 업로드 직후 문제은행을 생성해 기기에 내려받으면, 지하철에서 신호가 끊겨도 즉시 풀 수 있다.
3. **문제 배분은 코드가 정한다.** "골고루 내라"를 LLM에 맡기지 않고, 섹션별 할당량을 서버가 계산해 섹션 단위로 생성 요청한다.

## 1. 기능 ① — 파일 업로드 & 원문 숙지

### 1-1. 처리 흐름

| 단계 | 내용 | 비고 |
|---|---|---|
| 업로드 | 앱 → 스토리지(S3/GCS) presigned URL 직접 업로드 | 대용량은 multipart, 실패 시 이어올리기 |
| 형식 판별 | PDF / DOCX / PPTX / TXT / MD / 이미지 | 확장자 말고 MIME 매직바이트로 판별 |
| 텍스트 추출 | PDF 텍스트층 추출, DOCX·PPTX 파서, 이미지·스캔본은 OCR | 스캔 PDF는 텍스트층이 비어 있음 → OCR 분기 |
| 구조화 | 제목·목차 기준으로 **섹션** 분할, 섹션 안에서 **청크**(문단 단위) 분할 | 청크마다 `파일명·페이지·문단 번호` 앵커 저장 |
| 원본 보존 | 추출 텍스트 원문 + 해시(SHA-256) 저장 | 이후 변형 여부 검증 기준 |

### 1-2. "변형·추가·삭제 없음"을 보장하는 방법

- **저장 단계:** 추출 결과를 LLM에 통과시키지 않는다. 정리(공백 정규화 정도)만 하고 원문을 그대로 DB에 저장한다.
- **출제 단계:** 문제마다 `source_quote`(근거 원문 문장)를 필수로 받는다.
- **검증 단계:** 서버가 `source_quote`가 해당 청크 원문에 **글자 그대로 존재하는지** 문자열 매칭으로 확인한다. 없으면 폐기.
- **정답 검증:** 저가 모델(예: Claude Haiku 5.5)로 "이 근거 문장만으로 정답이 하나로 확정되는가"를 2차 판정. 애매하면 폐기.
- **외부 지식 차단:** 시스템 프롬프트에 "제공된 원문에 없는 사실로 문제나 선택지를 만들지 말 것"을 명시.

### 1-3. 여러 파일 동시 업로드

- 업로드 단위를 **학습 세트(Study Set)** 로 묶는다. 한 세트 = 파일 N개.
- 파일별로 독립 파싱 → 세트 단위로 섹션 목록을 합친다.
- 문제 배분 시 "파일 간 균등"과 "분량 비례" 중 사용자가 고르게 할 수 있다(기본: 분량 비례).

### 1-4. 파일 크기 제한 조사 결과

**결론: 앱·OS 자체의 강제 제한은 사실상 없고, 실질적 제한은 LLM API와 우리 서버 정책에서 온다.**

| 구간 | 제한 | 의미 |
|---|---|---|
| iOS / Android 파일 선택기 | 크기 제한 없음 | 메모리에 통째로 올리지 말고 스트리밍 업로드해야 함 |
| 클라우드 스토리지(S3 등) | 단일 PUT 5GB, multipart 최대 5TB | 사실상 무제한 |
| Claude Messages API 요청 | **요청당 32MB** | 초과 시 413 에러 |
| Claude PDF 입력 | **요청당 최대 600페이지** (200K 컨텍스트 모델은 100페이지) | 원본 PDF 직접 전달 시 적용 |
| Claude Files API | **파일당 500MB, 조직당 총 100GB** | 같은 파일을 여러 요청에서 재사용할 때 |
| 컨텍스트 윈도우 | 최신 모델 **1M 토큰** (Haiku 4.5는 200K) | 한 번에 읽을 수 있는 텍스트 총량 |

> 본 설계는 원문을 청크 단위로 나눠 섹션별로 요청하므로, 위 API 제한은 **"한 번의 요청" 단위**에만 걸리고 전체 파일 크기를 직접 제한하지는 않는다.

**권장 서비스 정책(초기값, 운영하며 조정):**

| 항목 | 무료 | 유료 |
|---|---|---|
| 파일당 최대 크기 | 20MB | 100MB |
| 세트당 파일 수 | 3개 | 10개 |
| 세트당 총 페이지 | 200p | 1,000p |

제한 근거는 기술보다 **비용**이다. 페이지 수가 문제은행 생성 비용에 거의 비례하므로 요금제와 연동한다.

## 2. 기능 ② — 객관식 문제 출제 (10/20/30/40문항)

### 2-1. 문제은행 방식

퀴즈를 요청할 때마다 생성하지 않고, 업로드 직후 **문제은행**을 한 번에 만든다.

- 은행 크기: 섹션당 최소 5문항, 세트 전체 최소 80문항(40문항 퀴즈 2회분).
- 생성은 비동기 작업 큐에서 실행. 급하지 않으면 Batch API로 비용 50% 절감.
- 완료되면 푸시 알림 → 앱이 문제은행을 로컬 DB(SQLite)에 저장.

### 2-2. 골고루 출제하기 (커버리지 균등)

**은행 생성 시 — 섹션별 할당량을 코드가 계산:**

```
섹션 i의 할당량 = 은행 총 문항 × (섹션 i 토큰 수 / 전체 토큰 수)
                  (단, 최소 3문항 보장, 짧은 섹션도 누락 없음)
```

LLM에는 **한 번에 한 섹션의 원문 + 생성할 문항 수**만 준다. 모델이 앞부분에만 몰아서 출제하는 문제를 구조적으로 막는다.

**퀴즈 구성 시 — 층화 추출:**

1. 사용자가 N(10/20/30/40) 선택.
2. 섹션별 출제 수 = N × 섹션 비율, 소수점 나머지는 라운드로빈 배분.
3. 각 섹션에서 **아직 안 푼 문제 → 오래전에 푼 문제** 순으로 뽑는다.
4. 최종 순서는 섹션이 섞이도록 셔플.

### 2-3. 중복 문제 방지

| 단계 | 방법 |
|---|---|
| 생성 시 | 각 문제에 `concept`(묻는 개념 한 줄) 태그를 받는다. 같은 섹션의 기존 concept 목록을 프롬프트에 넣어 "이미 다룬 개념 제외" 지시 |
| 저장 시 | 문제 본문 임베딩 코사인 유사도 0.9 이상이면 중복으로 폐기 |
| 출제 시 | 한 퀴즈 안에 같은 `concept` 두 번 금지, 최근 푼 문제는 쿨다운 |
| 은행 소진 시 | 미출제 문제가 N개 미만이면 해당 섹션만 추가 생성 |

### 2-4. 문제 생성 출력 스키마 (structured output)

```json
{
  "questions": [
    {
      "concept": "TCP 3-way handshake 순서",
      "stem": "TCP 연결 수립 과정의 올바른 순서는?",
      "choices": ["SYN → SYN-ACK → ACK", "ACK → SYN → SYN-ACK", "...", "..."],
      "answer_index": 0,
      "explanation": "원문 2장 3절에 따르면 ...",
      "source_quote": "클라이언트는 SYN을 보내고, 서버는 SYN-ACK로 응답하며 ..."
    }
  ]
}
```

- 보기 4개 고정, 정답 1개.
- 서버가 저장 시 보기 순서를 셔플하고 `answer_index`를 갱신(모델이 정답을 특정 위치에 몰아두는 편향 제거).

## 3. 기능 ③ — 오답노트

### 3-1. 규칙

- 퀴즈에서 틀린 문제는 자동으로 오답노트에 추가된다.
- 오답노트 문제를 다시 풀 때마다 `시도 수`, `정답 수`를 누적한다.
- **정답률 = 정답 수 / 시도 수** (오답노트에 들어오게 된 첫 오답 1회 포함).
- 정답률이 **70%를 넘으면(> 70%)** 오답노트에서 졸업(삭제) 처리한다.

### 3-2. 졸업까지의 흐름 예시

| 회차 | 결과 | 누적 | 정답률 | 상태 |
|---|---|---|---|---|
| 최초 퀴즈 | ✗ | 0/1 | 0% | 오답노트 추가 |
| 복습 1 | ✓ | 1/2 | 50% | 유지 |
| 복습 2 | ✓ | 2/3 | 66.7% | 유지 |
| 복습 3 | ✓ | 3/4 | **75%** | **졸업** |

→ 처음 틀린 문제는 **3번 연속 맞혀야** 졸업한다. 한 번 찍어서 맞힌 것으로 빠지지 않아 학습 효과가 있다.
→ 중간에 또 틀리면 졸업 시점이 늦어진다(예: ✗✓✗✓✓✓✓ → 5/7=71.4%에서 졸업).

### 3-3. 세부 설계

- **보기 재셔플:** 다시 풀 때 보기 순서를 섞어 "위치로 외우기"를 막는다.
- **삭제는 소프트 삭제:** `graduated_at` 기록만 남겨 통계·"졸업한 문제 다시 보기"에 활용.
- **오답노트 퀴즈 모드:** 정답률 낮은 순 → 오래 안 본 순으로 출제.
- **표기:** 문제 카드마다 `정답률 66% (2/3)` 와 졸업까지 남은 진행바 표시.
- **경계값:** 정확히 70%(예: 7/10)는 졸업 아님. 기획에서 "이상"으로 바꾸려면 비교식만 `>=`로 변경.

## 4. 데이터 모델

```
users(id, plan, created_at)

study_sets(id, user_id, title, status[uploading|parsing|generating|ready|failed], created_at)

files(id, set_id, filename, mime, size_bytes, page_count, sha256, storage_key)

sections(id, set_id, file_id, title, order_no, token_count)

chunks(id, section_id, order_no, text, anchor_page, anchor_para)   -- 원문 그대로

questions(id, set_id, section_id, chunk_id, concept, stem, choices_json,
          answer_index, explanation, source_quote, embedding, verified, created_at)

quiz_sessions(id, user_id, set_id, size[10|20|30|40], started_at, finished_at, score)

attempts(id, user_id, question_id, quiz_session_id, chosen_index, is_correct,
         source[quiz|wrong_note], answered_at)

wrong_notes(user_id, question_id, attempts, corrects, added_at, last_seen_at, graduated_at)
  -- PK(user_id, question_id)
```

오답노트 갱신 로직(서버·앱 공통):

```python
def on_answer(note, is_correct):
    note.attempts += 1
    note.corrects += int(is_correct)
    if note.corrects / note.attempts > 0.70:
        note.graduated_at = now()
```

## 5. 기술 스택 제안

| 영역 | 선택 | 이유 |
|---|---|---|
| 모바일 | React Native(Expo) 또는 Flutter | iOS/Android 동시 개발, 오프라인 DB 지원 |
| 로컬 저장 | SQLite (expo-sqlite / drift) | 문제은행·풀이 기록 오프라인 보관 후 동기화 |
| 백엔드 API | FastAPI(Python) | 문서 파싱 라이브러리 생태계가 Python에 집중 |
| 작업 큐 | Celery + Redis 또는 Cloud Tasks | 파싱·생성은 수 분 걸리는 비동기 작업 |
| DB | PostgreSQL + pgvector | 관계형 데이터 + 중복 판정용 임베딩 |
| 파일 저장 | S3 / GCS | presigned 업로드, 수명주기 정책 |
| 문서 파싱 | pypdf/pdfplumber, python-docx, python-pptx, OCR 엔진 | 형식별 분기 |
| LLM | Claude API (생성: Claude Opus 5.5, 검증: Claude Haiku 5.5) | 1M 컨텍스트, structured output, Batch API |
| 인증·결제 | Firebase Auth / Apple·Google 인앱결제 | 요금제별 업로드 한도 연동 |
| 푸시 | FCM / APNs | 문제은행 생성 완료 알림 |

**LLM 비용 감 잡기 (2026-10 기준 단가, 입력/출력 1M 토큰당):**
Claude Opus 5.5 $4/$20 · Claude Sonnet 5.5 $2/$10 · Claude Haiku 5.5 $0.10/$0.50.
품질 기준을 정한 뒤 Opus → Sonnet 순으로 실제 문서 샘플에서 비교해 생성 모델을 고른다.
같은 섹션 원문을 여러 번 보내므로 **prompt caching**을 켜면 반복 입력 비용이 크게 준다.

## 6. 개발 단계(로드맵)

| 단계 | 기간(예상) | 산출물 | 완료 기준 |
|---|---|---|---|
| **P0. 검증 실험** | 2주 | 파싱 + 문제 생성 스크립트 | 실제 교재 10종에서 근거 인용 일치율 ≥ 98%, 사람이 본 오류율 ≤ 3% |
| **P1. 백엔드 MVP** | 3주 | 업로드·파싱·문제은행 API, 작업 큐 | PDF/DOCX 업로드 → 80문항 은행 자동 생성 |
| **P2. 앱 MVP** | 4주 | 업로드, 퀴즈(10/20/30/40), 결과 화면 | 비행기 모드에서 퀴즈 풀이 가능 |
| **P3. 오답노트** | 2주 | 정답률 추적, 졸업 처리, 복습 모드 | 3-2의 시나리오 단위 테스트 통과 |
| **P4. 품질·운영** | 2주 | 문제 신고 버튼, 품질 대시보드, 비용 모니터링 | 신고율·폐기율·문항당 비용 지표 수집 |
| **P5. 베타 → 출시** | 3주 | TestFlight / 내부 테스트 트랙, 스토어 심사 | 개인정보처리방침, 업로드 파일 보관·삭제 정책 확정 |

### 품질 게이트 (CI에 포함)

- **원문 무결성 테스트:** 샘플 파일 추출 결과 해시가 기준값과 일치.
- **근거 인용 테스트:** 생성된 모든 문제의 `source_quote`가 원문에 존재.
- **배분 테스트:** 10문항 퀴즈에서 섹션별 출제 수가 할당량 ±1 이내.
- **중복 테스트:** 한 퀴즈 내 동일 `concept` 0건.
- **오답노트 테스트:** 시도·정답 시퀀스별 졸업 시점이 표 3-2와 일치.
- **회귀 평가셋:** 고정 문서 20종으로 모델·프롬프트 변경 시마다 오류율 비교.

## 7. 미리 결정해야 할 사항

1. **스캔본 PDF 지원 여부** — OCR 품질이 원문 정확성에 직결된다. MVP에서는 텍스트 PDF만 받고 이후 확장 권장.
2. **업로드 파일 보관 기간** — 저작권·개인정보 이슈. 원본은 문제 생성 후 N일 뒤 삭제, 추출 텍스트만 보관하는 방안 검토.
3. **"70% 넘으면"의 경계** — 초과(>)인지 이상(>=)인지. 본 문서는 초과로 설계.
4. **문제 난이도 옵션** — 단순 사실 확인형만 낼지, 응용형도 낼지. 응용형은 "원문 근거" 검증이 어려워지므로 초기에는 사실 확인형 위주 권장.
